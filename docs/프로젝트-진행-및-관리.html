0. 이 문서는

학생들의 웹 작업물을 캡처 시점 그대로 보존하기 위한 아카이브 시스템을, (1) 어떻게 만들고 진행해 왔는지, (2) 앞으로 어떻게 관리·운영하면 되는지 정리한 문서입니다. 담당자(교수·조교)가 바뀌어도 이 문서 하나로 이어받을 수 있도록 작성했습니다.

2026-07 개정: 온라인 사이트·자동화·클라우드(GitHub Actions·Pages·Docker)를 걷어내고, 폴더 하나가 곧 아카이브인 자족적 구조로 단순화했습니다. 실무는 "구글 시트에 링크 접수 → 캡처.command → 보기.command" 세 동작이면 끝납니다.

1. 프로젝트 개요

목적은 단순합니다. 학생들이 만든 웹사이트(대부분 GitHub Pages 포트폴리오)는 졸업·호스팅 만료·계정 정리 등으로 언젠가 사라집니다. 살아 있을 때 통째로 박제해 두어, 학기가 끝나고 몇 년이 지나도 그 시점의 모습을 그대로 탐색할 수 있게 하는 것이 목표입니다.

규모는 학기당 약 35명이며, 매 학기 반복하고 가능한 한 오래 — 평생 단위로 — 운영하는 것을 전제로 합니다. 그래서 모든 선택의 기준은 "10~20년 뒤에도 살아 있고 옮길 수 있는 기술인가"였습니다.

2. 왜 이렇게 만들었나 (설계 배경)

처음 참고점은 Rhizome의 Conifer였지만, Conifer 서비스는 2026년경 종료되었습니다. 다행히 Conifer를 만든 Webrecorder 팀의 후속 도구들이 더 오래 가는 형태(개방형 포맷)로 존재했고, 이 시스템은 그 포맷 위에 세웠습니다. 특정 서비스가 아니라 표준 파일에 베팅한다는 뜻입니다.

핵심 보존 원칙은 다음과 같습니다.

  • 개방형 표준만 쓴다 — 아카이브 포맷은 WARC/WACZ(ISO 28500 국제표준). 특정 회사가 사라져도 열 수 있습니다.
  • 서버에 의존하지 않는다 — 재생기는 브라우저 안에서 동작하므로 정적 파일만 있으면 됩니다. 관리할 서버·DB가 없습니다.
  • 프레임워크 churn을 피한다 — 사이트 본체는 빌드가 필요 없는 순수 HTML + 약간의 바닐라 JS. 썩을 빌드 단계가 없습니다.
  • 사람이 읽는 단일 출처 — 누가 무엇을 언제 캡처했는지는 텍스트 파일(manifest.csv) 하나로 관리합니다.
  • 복제가 곧 보존이다 — 폴더를 여러 곳(USB·드라이브)에 사본으로 둡니다.
  • 도구와 자산을 분리한다 — 캡처 도구는 소모품이지만 결과물(WACZ)은 표준이라 안 변합니다. 도구가 낡아도 이미 만든 아카이브는 영원히 유효합니다.

이 원칙에서 자연스럽게 나온 2026-07 결론이 "온라인 인프라를 걷어내고 자족적 폴더로"입니다. GitHub Actions·Pages·Releases·Docker는 편리하지만 2~3년마다 손봐야 하는 유지보수 부채였고, 오래 가는 핵심에는 필요 없었습니다.

4. 어떻게 진행했나 (작업 경위)
4.1 매니페스트 단일 출처

모든 것의 기준은 manifest.csv 한 파일입니다. 여기에 상태·URL·캡처 결과가 모입니다. 학생 목록은 이름순으로 정렬해 두었습니다.

4.2 1차 캡처

학생들이 제출한 URL을 모아 일괄 캡처했습니다. 대다수 작품이 정상 WACZ로 박제되었고, 압축 무결성 검사에서도 손상 없이 통과했습니다.

4.3 링크 깨짐 발견과 교정

1차 수집 때 URL을 스프레드시트(Numbers) 화면에서 눈으로 옮기는 과정에서 GitHub 아이디 철자가 한두 글자씩 틀린 경우가 다수 있었습니다(예: brgnmoru → brgnmorum, s000j6 → s000jing, yoandzhy → yoondzhy). 틀린 주소로 캡처되면 빈 페이지가 박제됩니다. 교수님이 주신 정본 링크와 매니페스트를 한 줄씩 대조하고, 교정한 URL이 실제로 살아 있는 작품 페이지인지 전수 확인한 뒤, 각 행의 notes에 무엇을 왜 고쳤는지 기록했습니다.

4.4 자족적 폴더로 재설계 (2026-07)

초기에는 GitHub Actions로 자동 캡처하고 Pages/Releases로 배포하는 클라우드 방식이었습니다. 오래 가는 관점에서 이는 유지보수 부채였으므로, 다음과 같이 단순화했습니다.

  • 캡처를 Docker(browsertrix) 대신 Playwright로 바꿔 로컬 Mac에서 바로 돌게 했습니다.
  • GitHub Actions·Pages·Releases와 중복 프론트엔드(site/)를 제거하고, 루트에 자족적 목록·재생 페이지 한 벌만 두었습니다.
  • 목록 페이지가 로컬 manifest.csv를 직접 읽도록 바꿔, 보는 시점에는 인터넷·구글이 전혀 필요 없습니다.
  • 구글 시트의 역할을 접수함(이름·수업·링크)으로 축소하고, 관리는 manifest.csv로 일원화했습니다.
5. 어떻게 관리하나 (운영 매뉴얼)
5.1 역할 분담 — 시트는 접수, CSV는 관리

구글 시트 = 접수함. 새 학생의 이름·수업(semester)·링크(original_url)만 넣습니다(학생이 직접 채우게 해도 됩니다). manifest.csv = 관리 원본. 캡처 결과·상태·메모 등 모든 관리는 여기서 합니다(Numbers·Excel·텍스트로 편집).

캡처.command가 시트의 새 학생만 manifest.csv로 가져와 pending으로 넣습니다. 이미 있는 학생의 관리 데이터는 절대 건드리지 않으므로 두 곳이 어긋나지 않습니다. 주의: 캡처 결과는 시트로 되돌아 쓰이지 않습니다 — 시트에서 상태·파일명 칸이 비어 보이는 것은 정상이며, 관리 현황은 admin.html에서 봅니다.

5.2 평소 3단계
  1. 접수(구글 시트) — 새 학생을 이름·수업·링크로 한 줄 추가.
  2. 캡처(캡처.command 더블클릭) — 시트의 새 학생을 가져오고, 대기 중인 사이트를 캡처해 wacz/<학기>/에 저장. 대상은 실행 중 물어봅니다(이름 필터를 비우면 대기 전체).
  3. 보기(보기.command 더블클릭) — 로컬 서버를 띄우고 브라우저로 목록·재생을 확인.

index.html을 직접 더블클릭하면 재생이 안 됩니다. WACZ 재생은 서비스워커를 쓰는데 이는 파일 직접 열기(file://)에서 동작하지 않으므로, 반드시 보기.command로 로컬 서버를 통해 엽니다. macOS 내장 파이썬만 있으면 되므로 보기에는 별도 설치가 필요 없습니다.

5.3 상태값(status)의 의미
status의미목록 노출
ok정상 캡처 완료, 재생 가능공개 (재생 가능)
pending (또는 빈칸)아직 캡처 전 (또는 URL 대기)대기 목록(admin)
recapture-needed다시 캡처가 필요함다음 캡처 대상
private / hidden학생 요청·저작권·개인정보 등으로 비공개공개 목록에서 숨김

wacz_file이 비어 있거나 status가 ok가 아닌 행은 목록에서 Archive 버튼이 생기지 않으므로, 캡처 전 학생이 잘못 재생될 걱정은 없습니다.

5.4 최초 1회 준비 (캡처하는 Mac에서만)

캡처에는 파이썬 도구가 필요합니다. 한 번만 설치합니다.

python3 -m pip install playwright warcio wacz
python3 -m playwright install chromium

보기만 하는 사람은 이 설치가 필요 없습니다. 처음 .command를 더블클릭하면 "확인되지 않은 개발자" 경고가 뜰 수 있는데, 파일을 우클릭 → 열기를 한 번만 하면 이후로는 그냥 더블클릭됩니다.

5.5 매 학기 루틴
  1. 학생들에게 공개 URL을 수집한다 (사이트가 살아 있을 때, 학기 중·직후).
  2. 구글 시트(접수함)에 그 학기 학생을 추가한다 — 이름·수업·링크만 (학기 태그 통일: 예 2026-fall).
  3. 캡처.command 실행 → 캡처.
  4. 보기.command로 각 작품이 제대로 재생되는지 점검한다 (특히 인터랙티브 작품).
  5. 부실 캡처는 manifest.csv에서 status를 recapture-needed로 바꾸고 다시 실행한다.
  6. 그 학기 결과가 반영된 폴더를 USB·드라이브에 복사해 백업한다.
5.6 백업과 장기 보존

저장 매체가 이 폴더 하나이므로 복제가 곧 보존입니다. 폴더를 최소 두세 벌(작업용 Mac·외장 USB·클라우드 드라이브 등)에 둡니다. 각 WACZ의 SHA-256이 매니페스트에 기록되어 있으니, 1년에 한 번 손상 여부(해시 일치)를 점검합니다. 재생기(replay/)가 먼 미래에 브라우저에서 안 돌더라도, 표준 WARC를 품은 WACZ는 그 시절의 다른 도구로 다시 열 수 있으므로 원본 WACZ 보관이 최우선입니다.

5.7 인수인계

다음 담당자에게 (1) 원본 폴더와 백업 사본의 위치, (2) 접수용 구글 시트 접근, (3) 사용법(이 문서·README), (4) 최초 설치(5.4)를 전달하면 됩니다. 시스템이 단순할수록 오래갑니다 — 이 시스템이 단순한 이유입니다.

7. 자주 생기는 문제와 대응
Archive를 눌렀는데 빈 화면

해당 WACZ가 wacz/<학기>/에 없거나(캡처 전), 파일명이 규칙과 안 맞는 경우입니다. admin.html에서 상태·캡처일을 확인하고, 없으면 그 학생을 다시 캡처합니다.

목록이 안 뜸 / "manifest.csv를 읽지 못했습니다"

index.html을 직접 연 경우입니다. 보기.command로 다시 엽니다(로컬 서버가 필요).

URL 오타

가장 흔합니다. 화면에서 옮길 때 한두 글자가 틀립니다. 캡처 전 브라우저로 실제 열어 정상 페이지인지 확인하면 빈 페이지 박제를 막을 수 있습니다.

파일명에 공백·한글

일부 작품은 이미지 파일명에 공백이나 한글이 들어 있습니다(예: 스크린샷 2026-...png). 캡처 후 이미지가 정상 표시되는지 눈으로 확인합니다.

인터랙티브 작품

클릭·스크롤·실시간 사운드 등 사용자 조작에 반응하는 작품은 자동 캡처가 일부를 놓칠 수 있습니다. 이런 경우 ArchiveWeb.page 확장으로 사람이 직접 조작하며 녹화하면 같은 WACZ로 시스템에 그대로 들어옵니다(파일명을 slug(이름)-slug(학기).wacz 규칙에 맞춰 wacz/<학기>/에 넣습니다).

외부 임베드(구글 슬라이드 등)

로그인이나 외부 서비스에 의존하는 링크는 재생 충실도가 떨어질 수 있습니다. 가능하면 학생에게 자체 호스팅된 공개 URL을 받는 것이 좋습니다.

저장 용량

영상·고해상도 에셋이 많으면 WACZ가 커집니다(작품당 수십~수백 MB). 학기가 쌓이면 폴더가 커지니 백업 매체 용량을 넉넉히 준비합니다.

8.2 매니페스트 컬럼

왼쪽 = 사람이 편집하는 칸, 오른쪽 = 캡처가 자동으로 채우는 칸(건드리지 말 것).

컬럼채우는 주체설명
student_name사람(접수)학생 이름
semester사람(접수)학기 태그 (예: 2026-spring). 폴더 이름이 됨
title사람작품 제목
original_url사람(접수)원본 사이트 주소 (공개·로그인 불필요)
status사람ok / pending / recapture-needed / private
notes사람비고 (교정 이력·주의사항 등)
drive_link사람(선택)구글 드라이브 자료 링크 → 목록에 Drive 버튼
wacz_file캡처 자동캡처 결과 파일명 (slug(이름)-slug(학기).wacz)
archived_date캡처 자동캡처 날짜
sha256캡처 자동무결성 점검용 해시

실제로 손댈 칸은 왼쪽 6~7개뿐입니다. 오른쪽 3개는 캡처가 알아서 채웁니다. (안 쓰던 type·wacz_url 칸은 없앴습니다.)

이 시스템의 미덕은 단순함입니다. 표준 포맷(WACZ) + 서버 없는 재생 + 텍스트 매니페스트 + 자족적 폴더 — 네 가지 모두 "10~20년 뒤에도 그대로 열린다"에 베팅한 선택입니다. 복잡한 것이 없으므로 고장 날 것도, 매년 손볼 것도 거의 없습니다.
