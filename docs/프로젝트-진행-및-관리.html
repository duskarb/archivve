1. 프로젝트 개요

목적은 단순합니다. 학생들이 만든 웹사이트(대부분 GitHub Pages 포트폴리오)는 졸업·호스팅 만료·계정 정리 등으로 언젠가 사라집니다. 살아 있을 때 통째로 박제해 두어, 학기가 끝나고 몇 년이 지나도 그 시점의 모습을 그대로 탐색할 수 있게 하는 것이 목표입니다.

규모는 학기당 약 35명이며, 매 학기 반복하고 가능한 한 오래 — 평생 단위로 — 운영하는 것을 전제로 합니다. 그래서 모든 선택의 기준은 "10년 뒤에도 살아 있을 기술인가"였습니다.

2. 왜 이렇게 만들었나 (설계 배경)

처음 참고점은 Rhizome의 Conifer였지만, Conifer 서비스는 2026년 6월경 종료되었습니다(신규 가입은 2025년 12월 마감). 다행히 Conifer를 만든 Webrecorder 팀의 후속 도구들이 더 오래 가는 형태로 존재했고, 이 시스템은 그 도구들 위에 세웠습니다.

핵심 보존 원칙은 다음과 같습니다.

  • 개방형 표준만 쓴다 — 아카이브 포맷은 WARC/WACZ(국제표준). 특정 회사가 사라져도 열 수 있습니다.
  • 서버에 의존하지 않는다 — 재생기는 브라우저 안에서 동작하므로, 정적 파일만 있으면 됩니다. 관리할 서버·DB가 없습니다.
  • 프레임워크 churn을 피한다 — 사이트 본체는 빌드가 필요 없는 순수 HTML + 약간의 바닐라 JS. 썩을 빌드 단계가 없습니다.
  • 사람이 읽는 단일 출처 — 누가 무엇을 언제 캡처했는지는 텍스트 파일(CSV) 하나로 관리합니다.
  • 복제가 곧 보존이다 — 원본 WACZ는 여러 곳에 사본을 둡니다.

4. 어떻게 진행했나 (작업 경위)
4.1 리포지토리 구성

코드(가벼운 텍스트)와 아카이브(무거운 WACZ)를 분리했습니다. WACZ는 .gitignore로 git 본문에서 제외하고, 빌드 때 site/wacz/로 모아 Pages에서 같은 출처로 재생합니다. 덕분에 리포 본체는 수 MB로 가볍습니다.

4.2 매니페스트 단일 출처

모든 것의 기준은 manifest.csv 한 파일입니다. 여기에 한 줄을 추가/수정하면, 자동화가 그 줄을 읽어 캡처하고 사이트 목록을 갱신합니다. 학생 목록은 이름 알파벳순으로 정렬해 두었습니다.

4.3 1차 캡처

학생들이 제출한 URL을 모아 일괄 캡처했습니다. 이 과정에서 대다수 작품이 정상 WACZ로 박제되었고, 압축 무결성 검사에서도 손상 없이 통과했습니다.

4.4 링크 깨짐 발견과 교정

1차 수집 때 URL을 스프레드시트(Numbers) 화면에서 눈으로 옮기는 과정에서 GitHub 아이디 철자가 한두 글자씩 틀린 경우가 다수 있었습니다(예: brgnmoru → brgnmorum, s000j6 → s000jing, yoandzhy → yoondzhy). 틀린 주소로 캡처되면 빈 페이지가 박제됩니다.

이를 바로잡기 위해, 교수님이 주신 정본 링크 목록과 매니페스트를 한 줄씩 대조하고, 교정한 URL이 실제로 살아 있는 학생 작품 페이지인지 전수 확인했습니다. URL이 비어 있던 일부 학생은 추정 주소가 실제로 정확한 것으로 확인되어 캡처 대기로 전환했습니다. 각 행의 notes 칸에 무엇을 왜 고쳤는지 기록해 두었습니다.

4.5 상태 정리

교정 결과, 정상 캡처되어 공개 중인 작품과, URL은 확정됐지만 (재)캡처가 필요한 작품, 그리고 아직 URL을 받지 못한 학생으로 구분해 매니페스트 상태값을 정리했습니다. 구체적 수치는 6장을 참고하세요.

5. 어떻게 관리하나 (운영 매뉴얼)
5.1 학생·작품 추가하기

manifest.csv에 한 줄을 추가합니다. 최소한 이름·제목·URL·학기를 채우고, 상태는 pending으로 둡니다. 나머지(파일명·해시·날짜)는 캡처 단계에서 자동으로 채워집니다.

5.2 상태값(status)의 의미
status의미사이트 노출
ok정상 캡처 완료, 재생 가능공개됨
pending아직 캡처 전 (또는 URL 대기)숨김
recapture-needed다시 캡처가 필요함숨김
private학생 요청·저작권·개인정보 등으로 비공개숨김 (색인에서도 제외)

비어 있는 wacz_file 행은 자동으로 사이트에 노출되지 않으므로, 캡처 전 학생이 목록에 잘못 뜰 걱정은 없습니다.

5.3 캡처 실행하기

GitHub 저장소의 Actions 탭에서 "Archive student sites" 워크플로우를 실행합니다. mode를 pending으로 두면 아직 캡처되지 않은(대기 중) 학생만 골라 캡처합니다. 필요하면 학기·이름 필터, 페이지 수·크롤 깊이도 지정할 수 있습니다. 매니페스트만 푸시해도 자동으로 돌도록 설정되어 있습니다.

참고: 캡처 엔진은 Docker로 동작하므로 캡처 자체는 GitHub Actions(또는 Docker가 있는 로컬 PC)에서 수행됩니다.

5.4 사이트 배포

매니페스트나 site/가 바뀌면 "Deploy archive site to Pages" 워크플로우가 index.json을 새로 만들고 WACZ를 모아 Pages에 배포합니다. 잘못 캡처된 옛 파일은 배포 때 폴더를 새로 만들며 자동 정리됩니다.

5.5 매 학기 루틴
  1. 학생들에게 공개 URL을 수집한다 (사이트가 살아 있을 때, 학기 중·직후).
  2. manifest.csv에 그 학기 학생들을 추가한다 (학기 태그 통일: 예 2026-fall).
  3. "Archive student sites" 실행 → 캡처.
  4. 사이트에서 각 작품이 제대로 재생되는지 점검한다 (특히 인터랙티브 작품).
  5. 부실 캡처는 옵션을 조정해 다시 실행한다.
  6. 그 학기 WACZ 묶음을 외부 백업에도 복제한다.
5.6 백업과 장기 보존

모든 WACZ는 최소 두세 벌, 서로 다른 위치에 둡니다(예: GitHub, 학교/개인 외장 저장소, 클라우드 객체저장소). 1년에 한 번 파일이 손상되지 않았는지(해시 일치) 점검합니다. 저장 총량이 수십 GB로 커지면 WACZ만 외부 저장소로 옮기고 사이트가 그 주소를 가리키게 하면 되며, 정적 방식이라 나머지는 그대로 둡니다.

5.7 인수인계

다음 담당자에게 (1) GitHub 계정 접근 방법, (2) manifest.csv에 줄 추가하는 법, (3) replayweb.page 고정 버전, (4) 백업 위치를 전달하면 됩니다. 시스템이 단순할수록 오래갑니다 — 이 시스템이 단순한 이유입니다.

7. 자주 생기는 문제와 대응
URL 오타

가장 흔합니다. 화면에서 옮길 때 한두 글자가 틀립니다. 캡처 전, 브라우저로 실제 열어 200으로 뜨는지 확인하면 빈 페이지 박제를 막을 수 있습니다.

파일명에 공백·한글

일부 작품은 이미지 파일명에 공백이나 한글이 들어 있습니다(예: 스크린샷 2026-...png). 캡처·재생 시 깨질 수 있으므로, 해당 작품은 캡처 후 이미지가 정상 표시되는지 꼭 눈으로 확인합니다.

인터랙티브 작품

클릭·스크롤·실시간 사운드 등 사용자 조작에 반응하는 작품은 자동 크롤링이 일부를 놓칠 수 있습니다. 이런 경우 ArchiveWeb.page 브라우저 확장으로 사람이 직접 조작하며 녹화하면 같은 WACZ로 시스템에 그대로 들어옵니다.

외부 임베드(구글 슬라이드 등)

로그인이나 외부 서비스에 의존하는 링크는 재생 충실도가 떨어질 수 있습니다. 가능하면 학생에게 자체 호스팅된 공개 URL을 받는 것이 좋습니다.

저장 용량

영상·고해상도 에셋이 많으면 WACZ가 커집니다. 단일 파일이 너무 커지면 외부 객체저장소로 분리합니다.
