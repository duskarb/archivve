# 수업 웹 아카이브 — 설계 문서 & 운영 가이드

> 학생 웹 작업물을 학기마다 장기 보존하기 위한 파이프라인 설계와 운영 매뉴얼.
> 핵심 방향: 특정 서비스가 아니라 **WARC/WACZ 표준 포맷 + 정적 재생 + 다중 백업**에 의존한다.
> 작성 기준일: 2026년 6월

---

## 0. 한눈에 보기 (TL;DR)

매 학기 약 30명의 학생 웹사이트를, **링크만 넣으면 자동으로 캡처되어 아카이브 사이트에 올라가는** 파이프라인을 만든다. 핵심 설계 원칙은 단 하나 — **"10년 뒤에도 옮길 수 있는 기술만 쓴다."** 그래서 빠르게 바뀌는 프레임워크나 특정 회사 서비스에 의존하지 않고, 국제표준 포맷과 서버 없이 동작하는 재생기, 사람이 읽을 수 있는 매니페스트, 그리고 복제 가능한 정적 파일 구조를 조합한다.

이 문서는 **MVP 구현안**과 **장기 보존 운영안**을 분리한다. GitHub Actions/Pages/Releases는 빠르게 시작하기 위한 좋은 MVP 도구이지만, 장기 보존의 유일한 저장소로 간주하지 않는다. WACZ/WARC 원본은 학교/연구실 소유 저장소, 기관 저장소, S3 호환 객체 저장소, NAS 등 최소 2곳 이상에 별도로 복제한다.

| 역할 | 선택한 기술 | 왜 10년 가는가 |
|---|---|---|
| 캡처(저장) | **browsertrix-crawler** (Docker) | WACZ/WARC 표준 출력, Webrecorder가 유지, 명령 한 줄 |
| 보존 포맷 | **WACZ (WARC 기반)** | WARC는 ISO 28500 국제표준. 도서관·국가기록원이 쓰는 포맷 |
| 재생 | **replayweb.page** | 서버 없이 정적 파일(js)만으로 재생. 백엔드 의존 0 |
| 자동화(MVP) | **GitHub Actions** | "링크 넣으면 자동 아카이브"를 CI가 수행. 단, 장기 운영에서는 학교/연구실 서버 cron으로 이전 가능 |
| 공개 호스팅(MVP) | **GitHub Pages (정적)** | 무료, HTML/JS만. 프레임워크 빌드 불필요. 다른 정적 호스팅으로 이전 쉬움 |
| 장기 원본 저장 | **학교/연구실 저장소 + 외부 백업** | GitHub를 유일한 보존 저장소로 보지 않고, WACZ/WARC 원본을 다중 복제 |
| 색인/메타데이터 | **사람이 읽는 CSV/YAML** | 10년 뒤에도 메모장으로 열림 |

> ⚠️ **중요한 맥락**: 교수님이 언급하신 **Rhizome의 Conifer**는 중요한 선례입니다. 다만 이 설계는 Conifer 같은 특정 호스팅 서비스 하나에 의존하지 않고, Webrecorder 생태계의 개방형 도구들(**WACZ/WARC + browsertrix-crawler + replayweb.page**)을 조합해 수업 자체의 장기 아카이브를 만든다. 즉 **Conifer의 정신은 잇되, 더 오래 옮겨 다닐 수 있는 방식**으로 만드는 것입니다.
>
> Conifer의 서비스 상태나 종료 일정은 교수님께 제출하기 전 반드시 공식 공지/이메일/기관 문서로 확인한 뒤 별도 주석으로 첨부한다. 출처가 불확실한 종료 일정은 본문에 단정적으로 쓰지 않는다.

## 1. 배경과 요구사항

교수님의 미션은 수업 학생들의 웹 작업물을 보존하는 것입니다. 문제는 **학생들의 Git 레포지토리나 개인 사이트는 언젠가 사라진다**는 점입니다(졸업, 호스팅 만료, 도메인 갱신 실패, 플랫폼 폐업). 따라서 "지금 살아있는 모습 그대로"를 박제해 두는 것이 목표입니다.

요구사항을 정리하면 이렇습니다.

- 규모: 학기당 약 30명, 매 학기/매년 반복, 가능하면 **10년 이상 지속 가능하고 다른 저장소로 이전 가능한 구조**로 운영
- 입력: 웹사이트 링크들을 넣으면
- 동작: **자동으로 아카이브되어 아카이브 사이트에 올라감**
- 결과물: 아카이브를 모아 보여주는 **아카이브 웹사이트**
- 제약: **최소 10년은 유지·이전 가능한 기술 스택**. 최신·급변 기술은 위험하므로 배제

이번 결정에서 합의된 방향은 (1) **정적 파일 방식**으로 운영, (2) **자동 크롤링**으로 캡처, (3) **GitHub 기반 MVP + 장기 저장소 복제**, (4) 산출물은 **설계 문서 + 운영 가이드**(이 문서)입니다.

## 2. 왜 이 기술 스택인가 — 10년 내구성의 원칙

웹 아카이빙은 사실 도서관·기록학계가 수십 년간 다듬어 온 분야입니다. 그곳의 디지털 보존(digital preservation) 원칙을 그대로 빌려오면, "10년 가는 설계"의 답은 거의 정해져 있습니다.

**원칙 1 — 개방형 표준 포맷만 쓴다.** 특정 회사의 독점 포맷은 회사가 사라지면 같이 죽습니다. 우리가 쓰는 **WARC**는 ISO 28500 국제표준이고, **WACZ**는 그 WARC에 색인·메타데이터·전문검색 인덱스를 곁들여 ZIP으로 묶은 패키지일 뿐입니다. ZIP과 WARC는 앞으로 10년이 아니라 수십 년이 지나도 열 수 있습니다.

**원칙 2 — 의존성을 최소화한다(서버리스).** 데이터베이스, 백엔드 서버, 로그인 시스템은 전부 "관리해야 살아있는" 것들입니다. 관리가 끊기면 죽습니다. **replayweb.page**는 서버가 전혀 필요 없습니다. 브라우저 안에서 Service Worker가 WACZ를 직접 읽어 재생하므로, 그냥 정적 파일(html, js, wacz)만 어딘가에 놓여 있으면 동작합니다. 이게 결정적입니다.

**원칙 3 — 프레임워크 churn을 피한다.** React/Next 같은 도구는 훌륭하지만 1~2년마다 호환성이 깨지고, 빌드 도구·노드 버전에 묶입니다. 10년 뒤 그 빌드를 다시 돌리는 것은 고통입니다. 그래서 아카이브 사이트 본체는 **순수 HTML + 약간의 바닐라 JS**로 만듭니다. 빌드 단계가 없으면 썩을 것도 없습니다.

**원칙 4 — 사람이 읽는 매니페스트.** 어떤 학생의 어떤 작품을 언제 캡처했는지는 **CSV 또는 YAML 텍스트 파일**로 관리합니다. 10년 뒤 도구가 다 바뀌어도, 텍스트 파일은 메모장으로 열어 내용을 이해하고 손으로라도 복구할 수 있습니다.

**원칙 5 — 복제가 곧 보존이다(LOCKSS).** *Lots Of Copies Keep Stuff Safe.* 한 곳에만 있으면 그 한 곳이 사라질 때 끝입니다. 그래서 WACZ/WARC 원본을 GitHub에만 두지 않고 학교/연구실 저장소 + 외부 저장소 + (선택) Internet Archive 등 **여러 곳에 복제**해 둡니다(8장). GitHub는 편리한 공개·배포 채널이지, 유일한 장기 보존 기관이 아닙니다.

**피해야 할 안티패턴**: 커스텀 백엔드 API, SQL 데이터베이스에 아카이브 저장, SPA 프레임워크로 만든 뷰어, 특정 클라우드의 독점 기능에 의존, 스크린샷 PDF만 남기기(인터랙션·링크가 다 죽음). 이번 설계는 이 모두를 의도적으로 배제합니다.

## 4. 컴포넌트 상세

### 4.1 캡처 — browsertrix-crawler

Webrecorder가 만든 도커 기반 고품질 크롤러입니다. 실제 브라우저(Brave/Chromium)를 띄워 페이지를 사람처럼 렌더링하며 돌기 때문에, 자바스크립트로 그려지는 현대 웹사이트도 충실히 잡습니다. 결과물로 **WACZ 파일 하나**가 나옵니다.

로컬에서 한 명 테스트하는 명령(도커만 설치되어 있으면 됨):

```bash
docker run -v $PWD/crawls:/crawls/ webrecorder/browsertrix-crawler crawl \
  --url https://student-portfolio.example.com \
  --scopeType prefix \
  --depth 5 \
  --generateWACZ \
  --collection hong-gildong-2026s
```

- `--url`: 학생 사이트 시작 주소
- `--scopeType prefix`: 그 사이트 안쪽(같은 경로 하위)만 따라가며 캡처. 외부 사이트로 새어나가지 않게 함
- `--depth`: 링크를 몇 단계까지 따라갈지(포트폴리오면 3~5면 충분)
- `--generateWACZ`: 결과를 WACZ로 패키징
- `--collection`: 결과 폴더/파일 이름. **`이름-연도학기`** 규칙을 권장

완료되면 `crawls/collections/hong-gildong-2026s/hong-gildong-2026s.wacz`가 생깁니다. 이 파일이 곧 "박제된 작품"입니다.

> 캡처 품질을 더 끌어올리는 옵션: `--behaviors autoscroll`(무한 스크롤 페이지 끝까지 내려가며 캡처), `--waitUntil networkidle2`(로딩 안정화까지 대기), `--text`(전문검색 인덱스 생성). 학생 사이트 유형이 다양하면 기본값으로 시작해 문제 생기는 케이스만 옵션을 추가하세요.

### 4.2 보존 포맷 & 저장 — WACZ/WARC + 다중 저장소

WACZ 파일은 보통 한 작품당 수 MB~수백 MB입니다. 영상·고해상도 이미지·음원·3D 에셋이 많으면 수 GB까지 커질 수 있습니다. 이걸 **Git 본문에 직접 커밋하면 레포가 비대해져** 나중에 느려지고 클론이 어려워집니다. 그래서 코드(텍스트)와 아카이브(대용량 바이너리)를 분리합니다.

저장소는 목적별로 나눕니다.

| 구분 | 권장 위치 | 역할 |
|---|---|---|
| 공개 재생 사본(MVP) | GitHub Pages의 `site/wacz/` | 아카이브 사이트가 같은 출처에서 WACZ를 읽어 재생 |
| 다운로드/보관 사본(MVP) | GitHub Releases | 학기별 WACZ 묶음 다운로드와 복제 출발점 |
| 장기 원본 | 학교/연구실 서버, NAS, 기관 저장소, S3 호환 객체 저장소 | GitHub와 무관하게 보존하는 원본 |
| 외부 백업 | 다른 클라우드, 외장 저장소, Internet Archive 등 | 단일 장애에 대비하는 복제본 |

GitHub Releases는 초기 운영과 다운로드에는 편리하지만, **장기 보존의 유일한 저장소로 간주하지 않습니다.** 학기마다 릴리스를 하나 만들어(예: 태그 `2026-spring`) 그 학기 학생들의 WACZ를 첨부하되, 같은 파일을 반드시 학교/연구실 소유 저장소 또는 S3 호환 객체 저장소에도 복제합니다. 브라우저 재생은 CORS 제한을 피하기 위해 Pages에 배포된 같은 출처 사본을 기본으로 씁니다. 나중에 저장 위치를 바꾸더라도 `index.json` 또는 매니페스트의 WACZ URL만 바꾸면 됩니다.

권장 용량 기준:

| 작품당 WACZ 크기 | 판단 | 대응 |
|---|---|---|
| 500MB 이하 | 일반 | GitHub Releases + 장기 저장소 복제 |
| 500MB~2GB | 주의 | 재생 속도 검수, 장기 저장소 우선 |
| 2GB 이상 | 대용량 | 객체 저장소 사용, 캡처 범위 재검토 |

> Git LFS는 작은 파일에는 가능하지만 무료 대역폭·스토리지 한도와 장기 운영 리스크가 있으므로 기본 저장소로 권장하지 않습니다.

### 4.3 색인/메타데이터 — 매니페스트

모든 것의 단일 출처(single source of truth)는 사람이 읽는 텍스트 파일 하나입니다. `manifest.csv`:

```csv
student_name,title,original_url,semester,wacz_file,archived_date,sha256,status,notes
홍길동,인터랙티브 자화상,https://gildong.example.com,2026-spring,hong-gildong-2026s.wacz,2026-06-10,,ok,
김아무개,사운드 웹페이지,https://kim.example.io,2026-spring,kim-2026s.wacz,2026-06-10,,review-needed,외부 API 일부 확인 필요
```

이 한 파일이 아카이브 사이트 목록과 자동화의 입력을 동시에 담당합니다. 10년 뒤 모든 도구가 사라져도 이 CSV만 있으면 누가 무엇을 만들었는지, 원본 주소가 무엇이었는지 알 수 있습니다.

### 4.4 재생 — replayweb.page (버전 고정 자가호스팅)

방문자가 작품을 "그 시절 그대로" 탐색하게 해주는 부분입니다. 핵심 장점은 **서버가 필요 없다**는 것. 브라우저 안의 Service Worker가 WACZ를 직접 읽어 캡처된 페이지를 복원합니다.

장기 보존을 위해 **CDN에 의존하지 말고 ui.js/sw.js 두 파일을 직접 받아 레포에 넣어** 둡니다(자가호스팅). 그러면 외부 CDN이 사라져도 사이트가 멀쩡합니다. 특정 버전을 받아 고정해 두면, 어느 날 업스트림이 바뀌어 동작이 깨질 일도 없습니다.

작품 하나를 임베드하는 최소 코드:

```html
<script src="replay/ui.js"></script>
<replay-web-page
  replayBase="replay/"
  source="wacz/2026-spring/hong-gildong-2026s.wacz"
  url="https://gildong.example.com">
</replay-web-page>
```

- `replayBase`: sw.js(백엔드 워커)를 불러올 위치 — 자가호스팅 폴더로 지정
- `source`: 재생할 WACZ의 위치. 브라우저 재생용으로는 Pages 같은 출처 경로를 권장
- `url`: 아카이브 안에서 처음 보여줄 시작 페이지

UI 없이 페이지만 꽉 차게 보여주려면 `embed="replayonly"` 속성을 추가합니다.

### 4.5 자동화 — GitHub Actions ("링크 넣으면 자동")

"링크를 넣으면 자동으로 아카이브에 올라간다"의 실체가 여기 있습니다. 매니페스트에 줄을 추가해 푸시하거나, 화면에서 버튼(workflow_dispatch)을 누르면 → CI가 컨테이너 안에서 크롤러를 돌려 WACZ를 만들고 → 릴리스에 올리고 → Pages를 다시 배포합니다. 사람이 도커 명령을 외울 필요가 없습니다.

> GitHub Actions 무료 한도(공개 레포는 무제한, 비공개도 월 2,000분)는 학기당 30명 규모에 차고 넘칩니다.

워크플로우 예시는 **부록 11.2**에 그대로 복붙할 수 있게 넣어 두었습니다.

### 4.6 품질검수 — 캡처 성공과 재생 성공은 다르다

웹 아카이빙에서 가장 흔한 실패는 "파일은 생성됐지만 재생해보니 핵심 인터랙션이 빠진" 경우입니다. 따라서 자동화 흐름에는 반드시 검수 상태를 넣습니다.

```
crawl
→ WACZ 생성
→ 체크섬 생성
→ ReplayWeb.page로 재생 확인
→ review-needed로 검수 목록에 표시
→ OK인 것만 Archive로 공개
→ 문제가 있으면 status=review-needed 또는 recapture-needed
```

권장 상태값:

| status | 의미 | 공개 여부 |
|---|---|---|
| `ok` | 재생 확인 완료 | 공개 |
| `review-needed` | 자동 캡처는 됐지만 사람이 확인해야 함 | 목록에 표시, Review 재생 가능 |
| `partial` | 일부 리소스/인터랙션 누락 | 공개 가능하나 주석 필수 |
| `recapture-needed` | 다시 캡처해야 함 | 숨김 권장 |
| `private` | 학생 요청/저작권/개인정보 문제로 비공개 | 비공개 |

검수 체크리스트:

- 시작 페이지가 열린다.
- 주요 링크/버튼/스크롤/인터랙션이 작동한다.
- 이미지, CSS, JS, 폰트가 크게 깨지지 않는다.
- 외부 API 의존 기능이 있다면 누락 여부를 notes에 기록한다.
- 개인정보, API 키, 비공개 토큰, 저작권 문제가 있는 자료가 노출되지 않는다.
- WACZ 파일의 SHA-256 체크섬을 매니페스트에 기록한다.

자동 검수는 한계가 있으므로, 학기 말에는 운영자가 각 작품을 최소 1회 직접 열어 확인합니다. 인터랙티브 작품이 많은 수업이라면 ArchiveWeb.page 같은 수동 캡처 도구를 병행합니다. 결과물이 같은 WACZ라 이 파이프라인에 그대로 넣을 수 있습니다.

### 4.7 아카이브 웹사이트 — 정적 인덱스

학생 작품을 학기별로 모아 보여주는 사이트입니다. **빌드 단계 없는 순수 HTML 한 장**이 본체이고, `manifest.csv`(또는 CI가 만든 `index.json`)를 읽어 카드 목록을 그립니다. 카드를 누르면 4.4의 replayweb.page 뷰어로 들어가 작품이 재생됩니다. 디자인은 자유지만, **핵심은 "프레임워크 없이도 동작"** 하게 두는 것입니다.

## 5. 제출 워크플로우 — 링크 → 자동 아카이브

운영자(교수님 또는 조교) 입장에서 한 명을 아카이브하는 전체 과정:

1. 학생에게서 **공개 URL**을 받는다(로그인 없이 누구나 접근 가능한 상태여야 함).
2. `manifest.csv`에 한 줄 추가한다: 이름, 제목, URL, 학기.
3. 변경을 GitHub에 저장(푸시)한다 — 웹 화면에서 바로 편집·커밋해도 된다.
4. **이후는 자동**: Actions가 크롤링 → WACZ 생성 → 체크섬 생성 → 공개 배포 사본 업로드 → 사이트 재배포.
5. 운영자가 ReplayWeb.page에서 재생 품질을 확인하고 `status`를 `ok`, `partial`, `review-needed` 등으로 표시한다.
6. 검수 완료된 작품이 아카이브 사이트에 나타난다.

학생 수가 많아도 매니페스트에 여러 줄을 한 번에 추가하면 일괄 처리됩니다. "링크 30개 붙여넣기 → 자동으로 30개 아카이브"가 됩니다.

> 더 매끄럽게 하려면(선택): 구글 폼이나 GitHub Issue 템플릿으로 학생이 직접 URL을 제출하게 하고, 그걸 매니페스트에 옮기는 식으로 접수 창구를 만들 수 있습니다. 다만 **핵심 파이프라인은 위 5단계로 충분**하며, 접수 창구는 나중에 얹어도 됩니다.

## 6. 단계별 셋업 가이드

### 6.1 사전 준비물

- GitHub 계정(교수님 또는 수업용 조직 계정 권장 — 담당자가 바뀌어도 계정이 유지되도록)
- (로컬 테스트용, 선택) Docker Desktop
- 도메인은 필수 아님. GitHub Pages 기본 주소(`<계정>.github.io/<레포>`)로 시작하고, 나중에 학교 도메인을 연결할 수 있음

### 6.2 레포지토리 구조

```
class-web-archive/
├── README.md                      # 이 시스템 설명 + 인수인계 안내
├── manifest.csv                   # 단일 출처: 누구의 무엇을 언제, 검수 상태
├── site/
│   ├── index.html                 # 아카이브 사이트(목록)
│   ├── viewer.html                # 개별 작품 재생 페이지
│   └── replay/
│       ├── ui.js                  # replayweb.page (버전 고정, 자가호스팅)
│       └── sw.js
├── .github/workflows/
│   └── archive.yml                # 자동화: 링크 → WACZ → 체크섬 → 배포
└── docs/
    └── 운영가이드.md              # 이 문서
```

### 6.3 replayweb.page 파일 받아 고정하기

`webrecorder/replayweb.page` 릴리스에서 `ui.js`와 `sw.js`를 받아 `site/replay/`에 넣습니다. 받은 **버전 번호를 README에 적어** 둡니다(예: "replayweb.page vX.Y.Z 고정"). 이렇게 하면 외부 CDN 없이, 그리고 업스트림 변경과 무관하게 영구히 동일하게 동작합니다.

### 6.4 크롤러 로컬 테스트(선택이지만 권장)

자동화를 켜기 전에 한 명만 4.1의 명령으로 로컬에서 돌려보고, 나온 WACZ를 [replayweb.page](https://replayweb.page)에 드래그해 제대로 재생되는지 눈으로 확인하세요. 캡처가 부실하면 `--depth`나 `--behaviors`를 조정합니다.

### 6.5 자동화 켜기

부록 11.2의 `archive.yml`을 `.github/workflows/`에 넣고, 레포 설정에서 **Actions에 쓰기 권한**과 **Pages 배포**를 활성화합니다. 이제 매니페스트에 줄을 추가하면 파이프라인이 돕니다.

### 6.6 아카이브 사이트 배포

레포 설정 → Pages에서 소스를 GitHub Actions로 지정하면, 배포가 끝날 때 사이트가 공개됩니다. 부록 11.3의 `index.html`을 시작점으로 쓰세요.

## 7. 학기별 운영 루틴 (체크리스트)

매 학기 말 반복하는 일은 이게 전부입니다.

- [ ] 학생들에게 공개 URL 수집(마감일 공지 — 사이트가 살아있을 때 잡아야 함)
- [ ] `manifest.csv`에 그 학기 학생들 추가(학기 태그 통일: 예 `2026-spring`)
- [ ] 푸시 → Actions 자동 실행 확인
- [ ] 각 WACZ의 SHA-256 체크섬 기록
- [ ] 아카이브 사이트에서 각 작품이 제대로 재생되는지 점검(특히 인터랙션 많은 것)
- [ ] `status`를 `ok`, `partial`, `review-needed`, `recapture-needed` 등으로 표시
- [ ] 부실 캡처는 옵션 조정 후 재실행 또는 수동 캡처 병행
- [ ] 그 학기 WACZ/WARC 묶음을 **학교/연구실 저장소와 외부 백업에도 복제**(8장)

## 8. 평생 보존 전략 (인수인계 포함)

"10년"을 넘어 "평생"으로 가려면, 기술 선택만으로는 부족하고 **운영 습관과 인수인계**가 필요합니다.

**3-2-1 백업.** 모든 WACZ/WARC를 최소 3벌, 2종류 매체, 1벌은 외부에 둡니다. 실무적으로는 (1) 학교/연구실 소유 저장소 또는 NAS, (2) 클라우드 객체저장소(R2/B2/S3 등) 또는 학교 기관 리포지토리, (3) GitHub Releases 또는 Internet Archive 같은 공개/외부 사본을 권장합니다. GitHub Releases는 유용한 사본이지만 유일한 원본이 되어서는 안 됩니다.

**정기 무결성(fixity) 점검.** 각 WACZ의 SHA-256 체크섬을 매니페스트에 기록해 두고, 1년에 한 번 파일이 손상되지 않았는지(같은 해시인지) 확인합니다. 체크섬이 달라지면 파일 손상 또는 잘못된 교체 가능성이 있으므로 백업본과 비교합니다.

**포맷 마이그레이션 감시.** WARC/WACZ는 당분간 안전하지만, 디지털 보존은 영원히 "지켜보는" 일입니다. Webrecorder의 공지와 표준 동향을 가끔 확인하고, 포맷 전환 권고가 나오면 그때 일괄 변환합니다. **원본 WARC를 품은 WACZ를 보관**하므로 미래의 어떤 도구로도 다시 처리할 수 있습니다.

**제3의 안전망 — Internet Archive(선택).** 정말 영구 보존을 원한다면 학생 사이트를 [web.archive.org](https://web.archive.org)의 Save Page Now로도 한 번씩 저장해 두세요. 우리 시스템과 독립적인 또 하나의 사본이 생깁니다.

**인수인계 문서.** 담당자(교수님/조교)는 바뀝니다. README에 (a) 계정 접근 방법, (b) 매니페스트에 줄 추가하는 법, (c) replayweb.page 고정 버전, (d) 백업 위치를 적어 두면, **다음 사람이 5분 만에 이어받습니다.** 시스템이 단순할수록 평생 갑니다 — 이 설계가 단순한 이유입니다.

## 9. 비용

초기 MVP는 거의 0원으로 시작할 수 있습니다. 공개 레포라면 GitHub Pages·Actions·Releases를 활용할 수 있고, 학기당 30명 규모는 대체로 충분합니다. 다만 장기 보존까지 고려하면 비용 항목을 현실적으로 분리해야 합니다. (1) 공개 사이트 운영은 무료 또는 저비용, (2) 장기 원본 저장소는 학교/연구실 인프라를 우선 사용, (3) 외부 객체저장소를 쓰면 총량에 따라 월 몇 달러~수십 달러가 발생할 수 있습니다. 비용이 생기는 지점은 저장용량, 다운로드 트래픽, 학교 도메인 연결입니다.

## 10. 리스크와 한계 (정직하게)

어떤 자동 아카이빙도 완벽하지 않습니다. 미리 알아 두면 좋은 한계들:

**자동 크롤링이 약한 케이스.** 로그인이 필요한 페이지, 사용자의 복잡한 조작에만 반응하는 인터랙티브 아트(드래그·마우스 추적·실시간 사운드), 외부 서비스에 의존하는 임베드(유튜브·외부 API)는 크롤러가 일부를 놓칠 수 있습니다. 지금은 "자동 크롤링으로 충분"한 작품 위주라 문제가 적지만, **나중에 인터랙티브 작품이 늘면** ArchiveWeb.page 브라우저 확장으로 사람이 직접 클릭하며 녹화하는 방식(예전 Conifer가 하던 일)을 병행하면 됩니다. 둘 다 결과물이 같은 WACZ라 **이 시스템에 그대로 들어옵니다** — 확장만 하면 됩니다.

**원본이 사라지기 전에 잡아야 한다.** 아카이브는 캡처 시점의 스냅샷입니다. 학생 사이트가 내려간 뒤에는 잡을 수 없으니, **학기 중/직후에 반드시 캡처**하는 게 핵심입니다(7장 루틴).

**GitHub 의존 리스크.** 호스팅을 한 곳에 의존하는 셈이지만, 우리 데이터는 표준 WACZ + 텍스트 매니페스트라 **언제든 통째로 들고 나갈 수 있습니다.** 정적 방식이라 다른 정적 호스팅(Netlify, 학교 서버, S3)으로 옮겨도 코드는 거의 그대로입니다. 즉 "갇히지 않는" 구조라 의존이 곧 종속은 아닙니다.

**대용량 작품.** 영상·고해상도 에셋이 많은 사이트는 WACZ가 커집니다. 2GB(릴리스 파일 한도)를 넘기면 객체저장소로 분리하면 됩니다.

## 11. 학생 제출 가이드

학생에게는 아래 조건을 미리 안내합니다. 아카이브 품질은 제출 방식에 크게 좌우됩니다.

- 작품 URL은 로그인 없이 접근 가능해야 합니다.
- 마감일 이후 최소 2주 이상 사이트를 공개 상태로 유지해야 합니다.
- 핵심 이미지, CSS, JS, 데이터 파일은 가능하면 같은 도메인 또는 같은 프로젝트 폴더 안에 둡니다.
- 외부 API, 실시간 서버, 유튜브/인스타그램/구글드라이브 임베드 등은 장기 재생에서 깨질 수 있습니다. 필요한 경우 대체 설명을 제출합니다.
- API 키, 비밀번호, 개인정보, 비공개 토큰을 코드나 HTML에 포함하지 않습니다.
- 저작권 문제가 있는 이미지/음원/영상 사용 여부를 확인합니다.
- 작품의 정확한 시작 URL과 작품 제목, 본인 이름/표기명, 공개 범위 동의 여부를 제출합니다.

권장 동의 문구:

> 이 프로젝트는 수업 아카이브의 일부로 장기 보존 및 공개될 수 있습니다. 원본 GitHub 저장소나 개인 사이트가 삭제되더라도, 제출 시점의 웹사이트 캡처본은 수업 아카이브에 보존될 수 있습니다. 개인정보, 비공개 API 키, 저작권 침해 자료를 포함하지 않았음을 확인합니다.

### 12.2 .github/workflows/archive.yml

```yaml
name: Archive student sites

on:
  workflow_dispatch:          # 화면에서 수동 실행 버튼
  push:
    paths: [ "manifest.csv" ] # 매니페스트가 바뀌면 자동 실행

permissions:
  contents: write             # 릴리스 업로드용
  pages: write                # Pages 배포용
  id-token: write             # Pages 배포 인증용

jobs:
  crawl:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Read manifest and crawl each site
        run: |
          mkdir -p crawls out
          python3 - <<'PY'
          import csv, os, subprocess, sys, hashlib

          failed = []
          with open("manifest.csv", encoding="utf-8-sig", newline="") as f:
              rows = list(csv.DictReader(f))

          for r in rows:
              url = (r.get("original_url") or "").strip()
              wacz = (r.get("wacz_file") or "").strip()
              status = (r.get("status") or "").strip()
              if not url or not wacz:
                  continue
              if status == "private":
                  continue

              coll = wacz.removesuffix(".wacz")
              print(f"::group::Crawling {url} -> {wacz}", flush=True)
              cmd = [
                  "docker", "run", "-v", f"{os.getcwd()}/crawls:/crawls/",
                  "webrecorder/browsertrix-crawler", "crawl",
                  "--url", url,
                  "--scopeType", "prefix",
                  "--depth", "5",
                  "--behaviors", "autoscroll",
                  "--generateWACZ",
                  "--collection", coll,
              ]
              try:
                  subprocess.run(cmd, check=True)
                  src = f"crawls/collections/{coll}/{coll}.wacz"
                  dst = f"out/{wacz}"
                  os.replace(src, dst)
                  h = hashlib.sha256(open(dst, "rb").read()).hexdigest()
                  print(f"SHA256 {wacz}: {h}")
              except Exception as e:
                  print(f"ERROR: {url} failed: {e}", file=sys.stderr)
                  failed.append(url)
              print("::endgroup::", flush=True)

          if failed:
              print("Some crawls failed; successful WACZ files will still be uploaded:", failed, file=sys.stderr)
          PY

      - name: Upload WACZ to a per-semester Release
        uses: softprops/action-gh-release@v2
        with:
          tag_name: ${{ github.event.inputs.semester || '2026-spring' }}
          files: out/*.wacz

  deploy:
    needs: crawl
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build static index from manifest
        run: |
          # manifest.csv -> site/index.json (사이트가 읽어서 카드 생성)
          python3 - <<'PY'
          import csv, json
          rows=[r for r in csv.DictReader(open("manifest.csv", encoding="utf-8"))]
          json.dump(rows, open("site/index.json","w",encoding="utf-8"),
                    ensure_ascii=False, indent=2)
          PY
      - uses: actions/upload-pages-artifact@v3
        with: { path: site }
      - uses: actions/deploy-pages@v4
```

> 위 워크플로우는 **개념을 보여주는 시작점**입니다. 실제 운영 전에 한 명으로 테스트하고, 릴리스 태그/학기 처리 방식을 팀 규칙에 맞게 다듬으세요. (요청 주시면 동작하는 레포 프로토타입까지 만들어 드릴 수 있습니다.)

## 마치며

이 설계의 미덕은 **단순함**입니다. 화려한 기술이 없기 때문에 고장 날 것도, 버전 올릴 것도, 돈 낼 것도 거의 없습니다. 표준 포맷(WACZ) + 서버 없는 재생(replayweb.page) + 텍스트 매니페스트 + 무료 정적 호스팅 — 이 네 가지는 모두 "10년 뒤에도 그대로 열린다"에 베팅한 선택입니다. Conifer가 보여준 브라우저 기반 웹 캡처의 방향을 계승하되, 특정 서비스에 묶이지 않는 표준 파일과 정적 구조로 만드는 것이라 방향도 옳습니다.

다음 단계로, 원하시면 **실제로 동작하는 레포 프로토타입**(매니페스트에 URL 넣으면 자동 아카이브되는 것)이나 **아카이브 사이트 디자인 템플릿**을 이어서 만들어 드리겠습니다.
